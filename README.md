# Регистрация с миграцией PostgreSQL

В этой версии есть только регистрация. Тестовый проект, отдельная библиотека моделей и авторизация не включены.

Начальная миграция `InitialIdentity` предназначена для новой пустой локальной базы. Она создаёт таблицы пользователей, ролей и связанных данных, но не переносит существующих пользователей.

## Запуск на другом компьютере

1. Установите Visual Studio с компонентами разработки ASP.NET, поддержкой .NET 10, .NET 10 SDK и PostgreSQL. Запустите сервер PostgreSQL.
2. В pgAdmin создайте новую пустую базу, например `shoestore_registration_local`. Пользователь PostgreSQL из строки подключения должен иметь права создавать в ней таблицы.
3. Откройте `ShoeStore.sln` в Visual Studio и дождитесь восстановления NuGet-пакетов.
4. Нажмите правой кнопкой на проект `ShoeStore` → «Управление секретами пользователя». Укажите свои параметры подключения:

   ```json
   {
     "ConnectionStrings": {
       "DefaultConnection": "Host=localhost;Port=5432;Database=shoestore_registration_local;Username=ВАШ_ЛОГИН;Password=ВАШ_ПАРОЛЬ"
     }
   }
   ```

   У этой версии отдельное хранилище секретов: настройки других копий проекта сюда не переносятся. Секреты находятся вне папки проекта и не попадают в GitHub. Не записывайте настоящий пароль в отслеживаемый `appsettings.json`.

5. Откройте «Сервис → Диспетчер пакетов NuGet → Консоль диспетчера пакетов». Выберите `ShoeStore` в поле «Проект по умолчанию» и как запускаемый проект. Выполните:

   ```powershell
   Update-Database -Args '--environment Development'
   ```

   Это команда консоли диспетчера пакетов, а не обычного терминала. Пакет `Microsoft.EntityFrameworkCore.Tools` уже подключён. Режим `Development` позволяет прочитать секреты пользователя без фабрики контекста. После установки пакетов при необходимости переоткройте консоль.

6. Выберите профиль запуска `http` и нажмите F5. Откроется страница регистрации. При первом запуске приложение создаст роль `Customer`, а при регистрации — нового пользователя и его имя.

## Что делает миграция

Создаются семь таблиц: `AspNetUsers`, `AspNetRoles`, `AspNetUserRoles`, `AspNetUserClaims`, `AspNetRoleClaims`, `AspNetUserLogins`, `AspNetUserTokens`. Сведения о применённой миграции записываются в `__EFMigrationsHistory`.

Повторное выполнение `Update-Database` не создаёт те же таблицы заново. Миграции не применяются автоматически при F5. После подготовки БД повторять настройку при каждом запуске не нужно.

При первом обновлении пустой БД используемый провайдер PostgreSQL может вывести `Failed executing DbCommand` для чтения ещё не созданной таблицы `__EFMigrationsHistory`. Это служебная проверка: если далее миграция применена и команда завершается `Done.`, обновление выполнено. Ошибки подключения, прав или создания таблиц нельзя игнорировать. Сообщения об ошибках в этой версии намеренно не скрываются.

Не применяйте начальную миграцию к существующим `shoestore` или `shoestore2`: в них могут уже быть таблицы без соответствующей истории миграций. Для этого сценария нужна новая пустая база.

Если у вас заданы переменные окружения `DOTNET_ENVIRONMENT` / `ASPNETCORE_ENVIRONMENT` или `ConnectionStrings__DefaultConnection`, проверьте их значения: они могут влиять на режим запуска и подключение. Перед обновлением убедитесь, что используется именно новая локальная БД.

## Альтернатива для обычного терминала

В папке проекта:

```powershell
dotnet tool restore
dotnet ef database update -- --environment Development
dotnet run --launch-profile http
```

Локальный инструмент `dotnet-ef` указан в `.config/dotnet-tools.json`. Для команды Visual Studio `Update-Database` установка этого инструмента не требуется.

Миграция не устанавливает PostgreSQL и не даёт доступ к базе другого человека: каждый разработчик использует собственную локальную БД.

Документация: [команды EF Core в Visual Studio](https://learn.microsoft.com/en-us/ef/core/cli/powershell).

# Тесты регистрации

Откройте `ShoeStore.sln` в Visual Studio. В решении три проекта:

- `ShoeStore` — приложение: страница регистрации, контроллер и подключение к БД.
- `ShoeStore.Models` — библиотека классов: `ApplicationUser` и `RegisterViewModel`. Содержит модели и правила проверки формы.
- `ShoeStore.Tests` — проект модульного тестирования MSTest. Он напрямую ссылается на библиотеку моделей и на приложение.

Приложение тоже ссылается на библиотеку, поэтому приложение и тесты используют одни и те же модели, а не их копии. Контроллер и контекст БД остаются в приложении.

Тесты доступны в меню «Тест → Обозреватель тестов». Для запуска сайта выберите `ShoeStore` запускаемым проектом.

В проекте используются .NET 10, MSTest, Moq и настоящий PostgreSQL для интеграционных проверок.

## Как объяснить тесты

В каждом тесте три шага: подготовить данные, вызвать проверяемый метод, сравнить результат с ожидаемым. `Assert` выполняет сравнение; несовпадение означает, что тест не пройден.

`TRegisterViewModel` — проверяет модель из библиотеки: меняет одно поле и запускает её атрибуты валидации. Например, `EmptyFirstName_ReturnsError` очищает имя и ожидает ошибку «Введите имя.».

`TAccountController` — вызывает настоящий контроллер. Moq заменяет работу с БД через `UserManager`: `Setup` задаёт результат операции, `Verify` проверяет, какие данные контроллер передал для сохранения. `TestInitialize` заново готовит контроллер перед каждым тестом.

`TRegisterIntegration` — отправляет форму на тестовый сервер приложения и проверяет записи в настоящей временной PostgreSQL. `PostgreSqlFixture` создаёт и удаляет эту БД, а `RegistrationApplicationFactory` запускает приложение с тестовым подключением.

Имена классов и методов — на английском. Комментарии и ожидаемые сообщения пользователю — на русском. Всего 26 проверок: 12 юнит, 11 с Moq и 3 интеграционные. `DataRow` запускает один метод отдельно для каждого набора данных.

## Быстрая проверка без базы данных

В терминале из папки проекта:

```powershell
dotnet test ShoeStore.sln --filter "TestCategory!=Integration"
```

Юнит-тесты проверяют обязательные поля, согласие с условиями, формат e-mail, минимальную длину пароля и совпадение паролей. Тесты контроллера с Moq проверяют успешную регистрацию, передачу имени и роли, повторный e-mail, русские ошибки и отмену создания пользователя при ошибке сохранения роли или имени.

## Все тесты, включая PostgreSQL

Нужен запущенный PostgreSQL и пользователь с правом `CREATEDB` (или администратор PostgreSQL). Создавать тестовую БД вручную не нужно.

В том же терминале задайте строку подключения к серверу для тестов, подставив свои параметры:

```powershell
$env:SHOESTORE_TEST_POSTGRES = 'Host=localhost;Port=5432;Database=postgres;Username=postgres;Password=ВАШ_ПАРОЛЬ'
dotnet test ShoeStore.sln
Remove-Item Env:SHOESTORE_TEST_POSTGRES
```

Пароль не добавляется в файлы проекта. Не публикуйте свою строку подключения. Переменная действует только для текущего процесса терминала и запускаемых из него процессов.

Для запуска из Обозревателя тестов Visual Studio должна быть запущена из процесса, которому уже задана эта переменная. Настройки подключения приложения и его User Secrets для интеграционных тестов не используются.

Если переменная не задана, три интеграционных теста будут явно отмечены как **пропущенные (Inconclusive)**, а не успешные. Если переменная задана, но сервер недоступен или нет прав создавать БД, тесты завершатся с ошибкой.

## Как изолированы интеграционные тесты

Каждый запуск создаёт новую БД `shoestore_registration_tests_<случайный идентификатор>` и создаёт в ней таблицы из `ApplicationDbContext`. Затем запускается настоящий код приложения на тестовом HTTP-сервере. Тесты открывают `/Account/Register`, получают защитный токен формы и отправляют данные с ним и cookie.

Проверяются создание пользователя, сохранение имени, назначение роли `Customer`, сообщение об успехе, хеширование пароля и запрет повторного e-mail. SQLite и подмена PostgreSQL базой в памяти не используются.

После завершения удаляется только временная БД, созданная этим запуском. Рабочая БД приложения не является целью тестов, даже если её имя указали в переменной: для служебного подключения используется `postgres`, для проверок — новое сгенерированное имя.

При принудительном завершении процесса временная БД может остаться. Удалять можно только оставшуюся БД с указанным префиксом, предварительно проверив её имя.
